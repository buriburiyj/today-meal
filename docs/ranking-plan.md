# 랭킹 시스템 설계 (구현 아님 — 설계 문서)

## Context

학습 스트릭·체크리스트 완료를 기준으로 사용자끼리 순위를 겨루는 랭킹 기능을 만들고 싶어 하신다. 지금 앱은 `studyLog`(script.js)가 **완전히 클라이언트(localStorage)에만** 존재하고, 이메일도 검증 없이 텍스트로만 받는 구조라(구독 시 비밀번호/토큰 없음 — 이전 리뷰에서 이미 지적된 부분), 랭킹처럼 "남에게 공개되고 서로 비교되는" 기능을 얹으려면 지금 구조로는 부족한 지점이 여러 곳이다. 아직 코드는 만들지 않고, 4가지 결정 사항과 단계별 진행 순서만 정리한다.

**범위 관련 중요 전제**: 이 저장소(today-meal)에는 **프론트엔드만** 있고, 실제 백엔드(Cloudflare Worker, `gitupsik-mail.buriburiyejun.workers.dev`)는 별도 저장소라 이 세션에서 그 코드를 볼 수 없다(CLAUDE.md 규칙상 Worker 코드/키는 이 repo에 절대 올리지 않음). 아래 저장소·인증 관련 추천은 일반적인 Cloudflare 아키텍처 지식과 지금 프론트엔드가 호출하는 API 패턴(`/subscribe`, `/getacademy`, `/setacademy` 등)에서 유추한 것이며, 실제 구현 단계에서는 Worker 저장소 쪽 작업이 따로 필요하다.

## 1. 사용자를 어떻게 구분할지

- **(A) 기기별 익명 ID** (localStorage에 랜덤 ID 생성, 로그인 없음)
  장점: 구현 매우 간단, 지금 앱의 "설정 없이 바로 쓰는" 성격과 잘 맞음.
  단점: 기기를 바꾸거나 브라우저 데이터를 지우면 그 사람의 랭킹 이력이 통째로 사라짐. 같은 사람이 여러 기기/시크릿창으로 계정을 무한히 만들어 상위권을 도배할 수 있음 — **랭킹은 "남과 비교되는" 기능이라 이 조작 가능성이 익명 메모 기능일 때보다 훨씬 치명적**이다.
- **(B) 이메일 기반 가벼운 인증(매직링크)**
  장점: 기기를 바꿔도 동일 정체성 유지, 이메일 1개당 랭킹 슬롯 1개로 제한 가능, 최소한의 신뢰 확보.
  단점: 지금 Worker가 이메일을 검증 없이 그냥 받기만 하는 구조라, 매직링크 발송·토큰 검증 로직을 새로 추가해야 함(다만 이미 구독 알림용 메일 발송 인프라가 있어 재사용 가능할 가능성이 높음).
- **(C) 소셜 로그인(구글 등)**: 신뢰도는 가장 높지만 개인 프로젝트 규모 대비 구현·운영 비용이 과함.

**추천: (B).** 랭킹은 "누가 몇 등인지가 남에게 보이는" 기능이라, 지금처럼 이메일을 그냥 텍스트로 받는 구조로는 시작하자마자 이름 도용이나 다중 계정으로 순위가 무의미해진다. 정식 회원가입까지는 필요 없고, 로그인 링크 이메일 발송 정도의 가벼운 인증이면 충분하다. (A)는 정식 오픈 전 프로토타입 단계에서만 임시로 쓸 수 있다.

## 2. 기록을 어디에 저장할지 — KV vs D1

- **Cloudflare KV**: 단순 key-value. 정렬/집계 쿼리가 없어서 "상위 N명 순위"를 뽑으려면 전체 목록을 매번 코드로 훑어 정렬해야 하고, list 연산이 최종적 일관성(eventually consistent)이라 데이터가 많아지면 느려지고 부정확할 수 있음. 지금 학원/디데이/구독 데이터 저장 방식으로는 적합하지만, 랭킹처럼 "정렬된 목록을 자주 조회"하는 용도엔 약함.
- **Cloudflare D1** (SQLite 기반): `ORDER BY`/`GROUP BY`로 학교별·반별 순위 계산이 자연스럽고, 인덱스로 빠르게 정렬되며 트랜잭션도 지원.

**추천: 랭킹 데이터만 D1으로 새로 추가.** 기존 학원/디데이/구독 데이터까지 옮길 필요는 없음(그건 지금도 KV로 충분) — 랭킹 전용 테이블(사용자, 스트릭/체크인 기록)만 D1에 만드는 "부분 도입"이 안전하고 비용도 적다. Worker에서 KV와 D1을 동시에 바인딩해 쓰는 건 Cloudflare에서 자연스럽게 지원된다.

## 3. 순위 기준

- **스트릭 일수(연속 완료일)**: 이미 `calcStreak()`(script.js)으로 계산 로직이 있어 재사용 가능. 다만 하루만 놓쳐도 0으로 리셋되어 변동성이 크고, 오래 쓴 사람이 압도적으로 유리해 신규 유저 동기부여가 약함.
- **완료율(체크한 항목 / 전체 항목)**: 항목을 일부러 적게 만들고 다 체크하면 쉽게 100%가 되는 조작에 취약함.
- **범위**: 전체 랭킹 vs 학교별 vs 반별 — 학교/반별이 접근성·동기부여 면에서 더 의미 있고(같은 학교 친구와 경쟁), 학교 정보는 이미 검색으로 확보되어 있어 그룹핑 자체는 어렵지 않음.

**추천: 스트릭 일수를 기본 지표로, 학교별 랭킹을 1차로 지원**(전체 랭킹은 이후 단계). 완료율은 조작에 약해서 동률 정렬 등 보조 지표 정도로만 사용.

## 4. 점수 조작을 어떻게 막을지

지금 `studyLog`는 100% 클라이언트(localStorage) 데이터라, 개발자도구로 직접 값을 바꿔서 존재하지 않는 연속 완료 기록을 얼마든지 만들어낼 수 있다. 지금은 비공개 개인 기록이라 문제가 없었지만, 랭킹으로 공개되는 순간 조작 유인이 생긴다.

- **클라이언트 값을 그대로 신뢰**: 구현은 쉽지만 조작에 완전히 무방비 — 랭킹의 신뢰 자체가 깨짐.
- **스트릭 계산을 서버(Worker)로 이전**: 클라이언트는 "오늘 학습 항목을 하나 이상 완료했다"는 이벤트만 서버에 보내고, 서버가 **서버 기준 오늘 날짜**로 하루에 한 번만 도장을 찍어 스트릭을 계산. 과거 날짜를 조작해 스트릭을 늘리는 건 원천 차단됨(단, 여러 계정을 만드는 방식의 조작은 여전히 가능 — 이건 1번 항목의 인증으로 막는 영역).

**추천: 스트릭 계산 로직을 서버로 이전**(클라이언트는 "오늘 완료" 신호만 전송). 완벽한 부정 방지는 아니지만, 지금의 "클라이언트 값을 그대로 믿는" 상태보다 훨씬 안전하고 구현 부담도 크지 않다.

## 단계 분할 제안

규모가 크니 한 번에 만들지 않고 아래 순서로 나눠서 진행하는 걸 추천한다. 각 단계는 지금까지처럼 별도 worktree + PR(병합) 단위로 진행.

1. **인증 추가 (매직링크 로그인)** — 랭킹의 전제조건. Worker 저장소 쪽 작업 필요.
2. **서버 사이드 체크인 API** — "오늘 완료" 이벤트를 서버에 기록하고 서버가 스트릭을 계산(D1 스키마 설계 포함). 조작 방지의 핵심.
3. **랭킹 조회 API + 프론트엔드 랭킹 화면** — 학교별 랭킹 우선 노출.
4. **(선택, 이후) 전체 랭킹, 완료율 보조 지표, 닉네임 설정, 어뷰징 모니터링** 등 부가 기능.

1~2단계는 Worker(백엔드) 저장소에서 진행해야 해서 이 세션(today-meal 프론트엔드 저장소)만으로는 끝까지 구현할 수 없다 — Worker 코드에 접근 가능한 환경에서 별도로 진행이 필요하다. 3단계부터는 이 저장소의 script.js/index.html 작업이 된다.
